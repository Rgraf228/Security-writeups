# Alert Investigation: MITRE ATT&CK T1078 (Valid Accounts) — Windows Logon Success

**Date:** June 2026
**Detection Source:** Wazuh (SIEM, self-hosted on home lab — Proxmox/Ubuntu)
**Affected Host:** Personal Windows PC (Wazuh agent: `windowsmachine`)
**Alert Type:** MITRE ATT&CK technique correlation, not a vulnerability finding

## Summary

The Wazuh dashboard's MITRE ATT&CK widget showed activity mapped to four tactics — Defense Evasion, Initial Access, Persistence, and Privilege Escalation — each with a count of 4. Investigation traced this to a single underlying rule (`rule.id: 60106`, "Windows Logon Success") firing five times in a ~14 minute window, mapped to MITRE technique **T1078 (Valid Accounts)**. Reviewing the raw event fields confirmed these were Windows service authentication events (Logon Type 5), generated by the OS Service Control Manager, not user logons or suspicious activity.

This write-up documents alert/detection triage, distinct from the CVE-based vulnerability triage in prior entries in this repo.

## Detection

Wazuh's MITRE ATT&CK dashboard (Framework view, filtered to agent `windowsmachine`) showed:

- Top Tactics: Defense Evasion (4), Initial Access (4), Persistence (4), Privilege Escalation (4)

Filtering Events by `rule.mitre.id: exists` and the affected agent returned 5 hits, all sharing:

- `rule.mitre.id`: T1078
- `rule.description`: Windows Logon Success
- `rule.id`: 60106
- `rule.level`: 3
- Timestamps spanning Jun 23, 2026, 17:05:55 – 17:19:40 (~14 minute window)

## Research

**MITRE ATT&CK T1078 ("Valid Accounts")** covers the use of legitimate credentials to gain or maintain access. It is associated with multiple tactics (Initial Access, Persistence, Privilege Escalation, Defense Evasion) because a valid authentication event can serve any of those purposes depending on context — which is why a single technique match populated all four tactic categories simultaneously in the dashboard.

The technique match is based on event type (a successful logon), not on contextual indicators of malicious intent (source, account type, time-of-day anomaly, etc.). A successful logon event matches this rule by definition; further investigation of the event's actual fields is required to determine whether the underlying activity is benign or suspicious.

## Investigation

Rather than treating the tactic labels as conclusive, I expanded one of the five underlying events to review the raw fields:

| Field | Value |
|---|---|
| `data.win.eventdata.logonType` | `5` |
| `data.win.eventdata.processName` | `C:\Windows\System32\services.exe` |

**Logon Type 5** corresponds to a **Service logon** in the Windows Security event logging schema — generated when a Windows service authenticates using its configured service account at startup. This is categorically different from Logon Type 2 (interactive) or Type 10 (RemoteInteractive/RDP), both of which would indicate an actual user session.

**`services.exe`** is the Windows Service Control Manager, the core OS component responsible for starting, stopping, and managing all registered services on the system. Its presence as the initiating process for a Logon Type 5 event is expected and consistent with normal service startup behavior, not anomalous activity.

## Conclusion

The five T1078-tagged events were generated by routine Windows service startup authentication, not by user logons, attacker credential use, or any other suspicious activity. The likely proximate cause was a Wazuh manager restart performed earlier in the same session (to apply a new local rule), which can result in the Wazuh agent service and/or related Windows services restarting and re-authenticating in sequence — consistent with the observed ~14 minute clustering of events.

**Action taken:** Closed as benign / no action required. No suppression rule was added for this finding, since `rule.id 60106` (Windows Logon Success) is a broad, frequently legitimate event type; suppressing it wholesale would reduce visibility into genuinely informative logon activity rather than just this one cluster. Documented here for reference instead.

## Lessons Learned

- **MITRE ATT&CK technique tags describe a category of behavior an attacker could exhibit — they do not confirm that an attacker did.** A technique match identifies which pattern an event resembles; it does not by itself establish intent or origin.
- **A single rule match can populate multiple "tactic" counts simultaneously.** A dashboard showing activity across several tactics does not necessarily indicate multiple distinct events or a multi-stage attack — it can reflect one technique that is associated with several tactics in the framework's own taxonomy.
- **Logon Type is one of the most useful fields for separating user activity from system/service activity** in Windows event data, and should be checked before drawing conclusions from a "logon" event of any kind.
- **Not every alert requiring investigation requires a suppression rule afterward.** Suppressing a high-value, broadly-scoped rule (like generic logon success) to silence one explained incident would reduce future visibility; documentation without suppression was the more appropriate outcome here.
